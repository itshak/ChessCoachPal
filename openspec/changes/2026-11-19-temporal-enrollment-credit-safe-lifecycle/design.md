# Design: temporal enrollment and prepaid entitlement

## Enrollment
Extend existing `workplace_enrollments` (not a second competing history table). Use inclusive user-facing dates `starts_on` and `ends_on` but half-open PostgreSQL `daterange(starts_on, ends_on + 1, '[)')` for non-overlap. Future cancelled rows require `cancelled_at`, `cancel_reason`; current/previous/future status is derived from dates and cancellation. Preserve legacy unknown starts explicitly, without manufacturing dates. New rows require starts_on. Teacher-local date is used for status. Exclusion constraint on teacher/student/workplace plus date range, ignoring cancelled rows. Existing student/workplace and tenant ownership checks remain.

## Archive preview and commit
Preview student revision, all current and future enrollments, recurring slots, future teaching sessions/participants, group memberships, credit packages with remaining units, invoice payment status, refund/dispute status and expiry dates. Block until every conflicting commitment has an approved disposition. Archive commit atomically closes ongoing memberships effective immediately, cancels future ones with audit, resolves commitments, archives student. No implicit credit consumption or financial write. Credit holds are implicit eligibility restriction from archived status plus explicit auditable hold reason; do not mutate original purchase validity dates. If original expiry passes during hold, show expired on return; any extension requires explicit policy and audited adjustment.

## Credit accounting
Existing `credit_packages` has teacher/student/invoice/workplace, credits, duration, price, starts_on/expires_on. `credit_redemptions` records one session redemption; balance is purchased credits minus valid redemptions and separately recorded explicit adjustments. Need to inventory cancellation/return receipts, invoice payments and refunds before deciding exact new ledger/adjustment table. Use immutable credit-adjustment events for transfer, forfeiture, refund or expiry extensions, with transaction-safe balance constraints and unique idempotency keys. Do not equate invoiced with paid; no transfer or refund without payer/account verification. No financial side effects from archiving by default.

## Reactivation
Preview each last completed enrollment per workplace (possibly several), plus held/expired credits and any future plans. Require explicit selected workplace IDs and start dates; commit reactivates and inserts fresh enrollment periods, without auto-redeeming credits. A package may be scoped to a workplace but never itself creates enrollment. For a package from a closed workplace, teacher must explicitly transfer or amend entitlement, not guess.

## MCP
Typed structured clarification: `code`, `missingFields`, `choices`, `previewDigest`, `expectedRevisions`, `retryTool`. Never flatten an expected ambiguity into a generic error. All mutation paths call the same service as website and database RPC, with idempotency and transactional enforcement.

## Data transition
The live-private-beta database has 28 students, zero current enrollments, 167 Yatmal historical attendance evidence rows (27 students); neither inspected DB has credit packages/redemptions as of 2026-11-19. Historical attendance is evidence only. Do not backfill active memberships from it automatically. Freeze candidate and checksum must be revised and tested on disposable DB before a single operator-approved cutover.

## Archived-student recovery from a new lesson intent (2026-11-21 amendment)

**Current observed source gap on main:** `teacherStudentNamesResolve` in `lib/server/lesson-capture-preview.ts` scans only `archived_at IS NULL`; consequently `ccp_lessons_capture_preview` reports `NOT_FOUND` for an archived-only name. The canonical single-student creator also filters out archived students, and `sessionsAdHocCreate` converts a missing approved enrollment into `NOT_FOUND`. The separate `ccp_students_lifecycle_preview/commit` exists but is not integrated into lesson capture. This describes source behavior, **not** a completed end-to-end runtime test.

1. **Identity resolution:** For *new-lesson intent only*, search the complete authorized teacher roster, including archived students, by stable student ID or normalized exact reporting name/stored aliases. Keep default active-only roster queries unchanged. Return bounded, safe `choices` with ID, display name and lifecycle status; never include foreign-tenant candidates, guess a partial match, pick active over archived when both match, or create a duplicate. Fail closed on incomplete pagination/unknown status. `NOT_FOUND` is only for no teacher-owned exact candidate; archived-only unique match returns `ARCHIVED_STUDENT_CONFIRMATION_REQUIRED` (or an equivalent typed clarification, not a 404).
2. **Read-only combined preview:** The shared website/MCP lesson-intent preview includes `studentId`, current `archivedAt`, student revision, existing last verified dated workplace periods and their provenance, selected workplace ID, proposed new period start, existing group/slot obligations, active-capacity preview, lesson kind (one-to-one, group scheduled or completed), local date/timezone, exact roster, schedule conflicts and applicable credit warnings. Use distinct outcome codes `CLARIFICATION_REQUIRED`, `ARCHIVED_STUDENT_CONFIRMATION_REQUIRED`, `CAPACITY_EXCEEDED`, `WORKPLACE_SELECTION_REQUIRED`, `PREVIEW_CHANGED`, `CONFLICT`, `FORBIDDEN` and true `NOT_FOUND`, with fields such as `missingFields`, `choices`, `retryTool`, and opaque preview digest/expected revisions. Do not expose private details until authorization/identity are established.
3. **Teacher options:** Present concise choices *Reactivate and create this lesson*, *Keep archived / cancel this lesson*, and *Choose another student*; optionally *Review a past lesson instead* when the date or intent implies historical work. An explicit “no” makes **zero** writes. For each archived member of a group, obtain approval of the exact identities and consequences in one coherent preview. An archived student's old workplace(s) can be offered as suggestions but **never silently reinstated**. A new workplace without verified prior membership requires its own authorized, reviewed enrollment path; the agent must not pretend the existing previously-verified-only lifecycle commit accepts it.
4. **Atomic transaction:** For the supported case of a verified selected workplace, a new canonical lesson in that workplace and explicit agreement to reactivate, implement a dedicated shared lesson+reactivation commit (e.g. `ccp_lessons_reactivate_and_create` backed by one SQL RPC). Validate a single `confirmed:true` approval bound to exact student IDs, workplace/date/roster, expected row revisions or opaque preview digest and idempotency UUID. Within row locks, recheck owner, enrollment constraints, quotas (including concurrent restores), schedule/DST conflicts, group roster semantics and exact lesson payload. Atomically reactivate only approved archived students, open only approved effective-dated periods, create **one** session/frozen roster and return a persisted receipt indicating lifecycle changes and lesson ID. Any failure rolls back *all* changes, including quota usage and group participants; a same-key replay returns the same receipt, changed payload conflicts. Existing confirmed lesson-only workflows remain valid for fully active enrolled students.
5. **No invented outcomes/financial effects:** New scheduled lessons remain unmarked for attendance; newly completed lessons require individually attested outcomes and no inferred material proficiency. Reactivation never automatically restores old groups/recurrences, credits, invoices, contacts, payer/portal rights, refunds or payment allocations. Credit availability and original expiration are reported independently. If a preferred workplace or capacity is unavailable, return a safe explanatory blocker and options to review another authorized workplace, resolve a slot or adjust capacity; no partial reactivation.
6. **Historical distinction:** Editing or correcting an existing older lesson and recording verified historical *presence dates* for an archived learner must not unarchive them. When asked to backfill a previously completed full lesson, first resolve the *historical* workflow, validate actual dated membership/source evidence and present explicit teacher-approved options; if no supported canonical historical writer can represent it, return `HISTORICAL_RECORDING_UNAVAILABLE` or equivalent structured guidance rather than fabricating a current lesson, enrollment, attendance or duration. Never infer a renewed coaching relationship merely from a past date.
7. **Client parity and security:** Website and MCP call the same preview and transactional service. Add a focused, individually reviewable discovery-friendly MCP workflow rather than a generic arbitrary executor. Keep name/alias collision cases, direct-ID calls, localized display, role/scopes and complete granular capability parity in CI. Confirm persisted state via independent read-back; never announce lesson creation from an advisory preview.
