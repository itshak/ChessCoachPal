# Proposed implementation design

This document is a design, not evidence of a deployed feature. Preserve the teacher-owned Supabase Auth + PostgreSQL RLS boundary, website parity, revision checks and authenticated `coach:read`/`coach:write` MCP grants. No CogNote or pre-1.0 compatibility is owed under ADR-0001; do not destructively reset a nonempty database.

## 1. Student profiles, Hebrew names and identity matching

**Canonical reporting identity:** Keep `students.id` UUID and `students.name` as the authoritative full legal/preferred **Hebrew** name when that is the teacher's convention. It is the name rendered in official reports, family/attendance exports and URLs' visible labels. Preserve Unicode NFC; don't auto-transliterate, replace or overwrite it with the alias from a chat request. The website provides one main "Name for reports (Hebrew or preferred full name)" and a separate "Short English name" plus multi-alias editor. Fully support RTL names and mixed-language UI.

**Search identity:** new `student_aliases(id, teacher_id, student_id, alias, alias_kind, search_key, created_at)`, alias kinds `english_short`, `english_full`, `hebrew_short`, `transliteration`, `nickname`, `former_name`. One convenient `preferred_short_name` may be a reference to an alias. `search_key` uses deterministic Unicode NFC/NFKC policy, case-fold, whitespace/punctuation normalization and optional explicit teacher-entered spelling variants; be conservative with Hebrew diacritics and phonetic variants. **Never choose silently between two student IDs with a shared alias.** Teacher-scoped duplicate aliases may exist, but matching returns `NEEDS_RESOLUTION` with canonical names, workplace and safe distinguishing hints; no unauthorized identifying metadata. Optionally maintain a teacher-confirmed alias mapping from real chat names only after explicit consent. Name changes retain stable student ID, and reports always show `students.name`.

**Profile:** propose `student_chess_profiles(teacher_id, student_id, strength_1_10 nullable CHECK 1..10, strength_assessed_at, strength_source, primary_time_control, chess_goals, focus_notes, updated_at)`. Overall `strength_1_10` is a **teacher-authored qualitative scale**, not a Chess.com or Lichess rating conversion; provide a clear rubric: 1 beginner, 5 developing intermediate, 10 advanced relative to teacher's program, with optional definitions and reviewer note. Store append-only `student_strength_assessments` (score, date, source, note, author, optional lesson) to show trends. When no assessment exists, show **Not assessed**, not 0 or a generated score. Agents may propose an **unverified** assessment but only teacher confirmation can change the official score. Existing inherited `skill_assessments` (1–5 per dimension) and `chess_observations` (agent proposals vs teacher approval) remain separate; consolidate UI terminology and source indicators, not overwrite them. Per-student goals, focus areas and assignments can leverage existing categories/notes, with explicit progress/source history rather than one opaque text blob.

**External identity:** new `student_chess_accounts(teacher_id, student_id, provider CHECK lichess|chess_com, username, profile_url, claim_status [teacher_entered|public_profile_found|owner_confirmed], visibility, sync_enabled, last_checked_at, last_error_code)`. One primary account/provider by default, with explicit future multiple-account support. Normalize provider-specific username for matching but preserve original casing. A URL is not proof of account ownership. Never capture credentials for a student's Lichess/Chess.com account; public read-only profile is enough. Teacher-side Lichess Study OAuth token is stored in a completely separate encrypted `lichess_connections` table.

**Ratings:** proposed `student_rating_snapshots(teacher_id, student_id, chess_account_id, provider, time_control, rating nullable, rating_deviation nullable, provisional nullable, games nullable, observed_at, fetched_at, source [provider_api|teacher_manual], raw_etag nullable)`, unique/idempotent per provider/account/category/source/observation timestamp. Render current latest snapshot **per provider and time control** (rapid, blitz, bullet, classical/daily, puzzles where available); show "not available" for absent values and provider-specific provisional indicators; don't call a single numeric cell "Lichess rating." Preserve historic series and source/last sync/403/404/429 status. `GET https://lichess.org/api/user/{username}` (or rating/perf endpoints) and Chess.com read-only `GET https://api.chess.com/pub/player/{username}/stats` support public rating lookup where supplied; fetch with bounded rate limits/If-Modified-Since/ETag, service User-Agent, cache and opt-in. These ratings are **not comparable across platforms or time controls** and do not automatically alter 1–10 teacher strength. For minors, require teacher authorization/appropriate lawful basis; default off for automatic public lookup. Never use user-submitted arbitrary URL as a proxy target.

**Privacy:** full names/contact data, birthdate, guardians, private notes, history and linked external identities are teacher-private. MCP normal list/resolve tools expose only IDs, report/short name, selected workplace, permitted strength/rating summary if needed—not guardian contact data, birthdate or hidden notes. Export/deletion follows existing self-hosting policy and future SaaS privacy controls. Tenant composite FKs/RLS and cross-teacher tests for each new table.

## 2. One canonical lesson history and scheduled fallback

Current `lesson_slots/lessons` and `teaching_sessions/session_participants/session_attendance` overlap. Unify canonical session history so one simultaneous 13:00–14:30 lesson with Armond, Shushana and David counts **90 teacher minutes, not 270**. Add explicit ad-hoc participant-set session mode without manufacturing a group or silently enrolling students. Preserve the frozen roster. Weekly student slots remain scheduling input for missing-time inference; reconcile materialized `lessons` with sessions or migrate to one canonical projection on a **fresh install**. No double compensation, attendance, reports or attendance rates. Scope each slot to teacher/student/workplace, weekday/timezone/effective dates and exceptions, and make it MCP-readable/editable.

`teacher_context_get` returns trusted teacher local date, locale, IANA timezone and workplace options; `students_resolve` searches aliases and full names, not guesses; `schedule_slots_list` and `schedule_day_preview` provide candidate occurrences; `materials_studies_search` and `materials_chapters_search` resolve actual PGN chapter. `lessons_capture_preview` returns reviewed student IDs, chosen workplace, time source (explicit or scheduled), DST warnings, actual chapter if verified, 3 attendance statuses, **unknown comprehension** for each student, conflicts, expected data revisions, expiry, digest and next-step questions. A preview never mutates.

Explicit start/end overrides slot inference; omitted hours use a **single unambiguous common scheduled occurrence** for the students. If 3 different per-student slots conflict, ask rather than invent a composite time. Local "today" must use the teacher's configured zone even if client zone differs; report UTC instant plus local offset. If overlap/conflict exists, ask or reject; do not make repeated saves on retry.

`lessons_capture_commit({previewId,digest,idempotencyKey,confirmed:true})` rechecks versions and atomically writes one teaching session, roster, attendance, session material and per-student material history within one PostgreSQL transaction. `coach:write` scope and teacher account are mandatory; idempotency binds preview/client/teacher and rejects modified replay. Return minimal structured receipt plus deep link and pending/unresolved annotations. Correcting the same lesson on the website updates the canonical record, optimistic revision and MCP next reads.

## 3. Lichess materials management and study selection

The **Materials → Lichess** website page supports teacher-owned OAuth2/PKCE `study:read`, optional separate explicit `study:write` (or teacher-entered encrypted PAT alternative), account identity/scopes, reconnect/revoke, safe metadata sync, study/chapter search, and teacher/workplace/student priority and puzzle-study configuration. The provider token is server-only, encrypted separately from the MCP grant; never expose through tool results, prompts, logs, or child accounts. Lichess OAuth lacks standard refresh tokens; represent expired/revoked status and reconnect.

Proposed `lichess_connections`, `material_studies`, `material_chapters`, `material_preferences` (lesson/puzzle, teacher/workplace/student scope and clear precedence), `session_materials`, `student_material_history`, and `external_write_intents` tables: all keyed by teacher and stable provider IDs with RLS. Index bounded metadata/PGN tags (White/Black/Event/Date, ordinal, name, study/chapter ID) and last-checked status; avoid indefinite duplication of private PGNs in the database. Use fixed-host Lichess endpoints: authorized study listing, PGN export, study creation and PGN chapter import. Check current API limits when implemented; respond to 401/403/429/5xx with structured errors, serialized requests and cooldown. **User-specified accessible study** overrides defaults for this session and the associated named students without silently updating saved preferences.

Resolve "Steinitz vs Chigorin" by actual PGN metadata; "Classic Games 2 game 32" is a **1-based displayed chapter ordinal** requiring confirmed provider study/chapter IDs, not invented historical game identity. Multiple games/chapter matches require user choice. On provider outage, allow teacher-confirmed pending/unverified source reference, never assert a verified chapter or grant provider access beyond permission.

## 4. Chessboard image → verified FEN → puzzle study

Client image handling is **capability-dependent**: a vision-capable ChatGPT/Codex conversation may infer board pieces and orientation and call structured `chess_fen_validate` with a *candidate* FEN. MCP does not automatically receive an image; website fallback offers a board editor and manual FEN input (any image/OCR upload needs a separately tested bounded implementation). A still image cannot determine all state (side to move, castling, en-passant and move counters). Validate 6-field FEN, piece counts/kings, pawns, turn and legality consistency using a maintained chess rules library; ask for unknowns and present exact board preview. Never silently manufacture missing rights, or publish an unconfirmed position.

Serialize PGN with `[SetUp "1"]` and `[FEN "..."]`, deterministic chapter label/fingerprint and `[Result "*"]`. `puzzles_position_preview` chooses explicit puzzle study > student/workplace/teacher preferences > approved new Puzzles study. `puzzles_position_publish` needs `coach:write`, provider `study:write` and approval. Check live chapter count (Lichess up to 64 chapters) and account creation limits (up to 30 new studies/day); account for initial study starter chapter. For a full study, allocate collision-safe `Puzzles 2`, `Puzzles 3` successor in same series and confirm before provider creation. Never delete unrelated chapters as a capacity workaround.

External POST is not atomic with the internal SQL transaction. Store provider-write intent/PGN hash **before** remote call, reconcile timeout by searching exact deterministic chapter fingerprint/study IDs, then record resolved IDs. Never duplicate a chapter or numbered study on retries. If no permission/quota/network, keep a pending local draft and actionable error rather than a false Lichess success. Provider writes should be restricted by per-teacher rate limits and serialized near-capacity study locks.

## 5. Tool contracts and review boundaries

One shared Zod schema catalogue feeds MCP discovery and OpenAPI. Keep existing 28 exact `ccp_v1_*` tool names and add [proposed names](tool-catalog.md). Distinguish read/resolve (no mutation), teacher-confirmed local writes, and separately provider-authorized external writes. No broad SQL, no student credentials or online platform account mutations, no implicit learner skill scores and no uncontrolled mass edits. Student roster bounded at 100 with one explicit preview-bound action.

Errors: `NEEDS_RESOLUTION`, `MISSING_SCHEDULE`, `TIME_AMBIGUOUS`, `CONFLICT`, `SOURCE_UNVERIFIED`, `NEEDS_AUTH`, `RATE_LIMITED`, `PROVIDER_UNAVAILABLE`, `CAPACITY_REACHED`, `STALE_PREVIEW`, `DUPLICATE_OR_PENDING`, `FORBIDDEN`, with sanitized IDs only. Independently verify website parity, revocation, denied cross-teacher IDs and provider-token non-disclosure.

## 6. Phasing and acceptance

A. Student profile/account/rating schema + website + MCP identity and progression tools.
B. One canonical schedule/session and ad-hoc multi-roster capture preview/commit.
C. Lichess account/material chapter index and study assignment.
D. Position validation/publishing and bounded study rotation.
E. Synthetic GitHub CI/real DB E2E/provider mocks, tenant/outage tests, updated applied specs and docs only after actual code exists.

No real Lichess account needed in CI. Live ChatGPT/Claude compatibility is a separate final v0.1.0 publication gate. Public SaaS/Plugin Directory launch is not part of this implementation.
