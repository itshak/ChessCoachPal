# Change: freeze unified operator-only SaaS schema and repair regressions FIRST

**Status:** Proposed; mandatory implementation prerequisite, not accepted or deployed. **Priority:** P0, first remaining implementation change. **Depends on:** archived baseline-first contract, ADR-0017 and ADR-0018. **Blocks:** every remaining active feature/UI/locale/portal/rating/finance/professional OpenSpec implementation phase until schema and regression gates are green.

## Why
The active changes currently overlap in teacher-owned Contacts, scoped portal grants, financial ledger, workplace context, FIDE/national/online ratings, recurrence and lifecycle. Applying feature proposals sequentially risks changing the canonical schema repeatedly and leaving broken consumers. Establish one complete target schema and repair all schema-induced website/MCP regressions before continuing any feature proposal. Current PR #104 is a draft candidate containing substantial baseline and service changes; passing automated E2E does not certify a final schema, real-data reconciliation or feature completion.

## Scope (schema and regression ONLY)
1. Inventory all active OpenSpec designs, current canonical SQL, generated types, website/MCP read/write paths, RLS/grants, financial and historical data. Publish a table-by-table gap matrix and explicit owner for each schema concept; reuse existing structures rather than duplicating them.
2. Finalize **one** `supabase/migrations/20261107000000_chesscoachpal_baseline.sql` for Contacts, students, multi-workplace context, scoped portal grants, compensation/obligations/payments, FIDE and national membership/rating evidence, consented online rating-sync consent/queue/receipts/status, and any genuinely persisted lesson lifecycle/recurrence exceptions/audit. Derive daily queues from existing data unless persistence is justified. Preserve independent educational strength/mastery versus external ratings; preserve immutable historical financial evidence.
3. Enforce ADR-0018 operator-only SaaS: shared tables, authenticated teacher UUID as tenant key, tenant-safe composite FKs, owner-leading indexes, RLS and strict privileged-role boundaries. No per-coach database/schema, customer self-hosting, sharding implementation or microservice rewrite.
4. Regenerate SQL/TypeScript contracts, update schema inventory, seed/test fixtures, adapters and any currently implemented UI/MCP consumers that break against the finalized schema. Fix regression root causes, not tests/assertions; do not deliver the **new** planned business functionality, provider automation, UI redesign or professional workflow features in this change.
5. Validate fresh empty installation, grants/RLS, negative cross-tenant reads/writes, idempotent ledger/rating-job constraints, Auth/Storage integration, full CI/typecheck/unit/security, authenticated browser↔delegated MCP E2E, Compose and backup/restore; independent read-back and historical-data preservation checks. Ensure all active proposals can target the frozen schema without further planned schema edits.
6. Produce a schema freeze manifest, deferred feature checklist and release handoff. Real production transition is **separately authorized** under ADR-0017, with historical financial/portal/Storage reconciliation; source-only success never authorizes cutover, merge, release or customer data changes.

## Out of scope
No automatic public provider fetch, background scheduling in production, UI redesign, new customer-facing workflows, customer hosting, per-tenant DB provisioning, sharding, live migration or data reset. Minimal compatibility repairs for **already implemented** consumers are in scope; old pre-v1 compatibility layers are not.

## Acceptance
Canonical baseline includes all approved schema requirements from active proposals; no duplicate finance/rating/consent tables; all schema guards and exact-head CI/E2E/security/Compose/restore pass; tenant A/B negative tests and cross-tenant FK injection are denied; current website/MCP parity does not regress; independent schema freeze inventory is reviewed; all downstream OpenSpec changes reference this change and are limited to functionality against its schema. Do not claim that downstream features are implemented merely because their tables exist.
