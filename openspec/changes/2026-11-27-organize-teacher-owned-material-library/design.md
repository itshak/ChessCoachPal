# Design: flexible collections, not a forced chess taxonomy

## Domain decisions (proposed)
Call the organizing entity a collection (folder/category in user-facing language). Recommend dedicated library collections rather than repurposing chess_skill_categories: skill observations assess learners, while arbitrary collections can mean "Junior club", "My favourite games" or a course. Keep these independent; an explicit future mapping may link a collection to a skill but does not imply assessment. Do not use learning_material_relations (extracted_from, derived_from, prerequisite) as folder edges.

Logical model for schema review, not DDL authorization:
- Collection: teacher_id, stable UUID, nullable parent UUID, name, optional description, sibling order, archive state, revision and timestamps.
- Membership: teacher_id, material_id, collection_id, optional sibling ordering if needed, unique owner/material/collection tuple. Material identity, type, provider IDs and teaching history remain unchanged. Membership has no workplace ownership; workplace-filtered evidence remains scoped.
- Same-owner composite references, active sibling name normalization/uniqueness (Unicode/localized display retained; decide exact normalization in review), no self-parent, cycles or cross-owner edges. Stable IDs survive rename and move. Bounded name length, depth, batch size, pagination and query budget; define concrete technical limits at schema review, not pricing/teaching restrictions.
- Review tree mutation serialization under a teacher-scoped transactional lock; prevent concurrent opposite moves creating cycles, stale revisions, duplicate membership or partial template application. Use request receipts/digests and independent read-back.
- Archive a collection through explicit impact preview (descendants and memberships); proposed safe default archive subtree, preserve materials/history and membership links; archived branches omitted from active navigation, All materials remains accessible. Uncategorized means no active membership, not a stored category. Restore must resolve archived parent or sibling conflict explicitly, never silently rename or move. No destructive cascade into materials. Removing membership is distinct from archiving/deleting material. No hard-delete feature in initial scope unless separately reviewed.
- Export stable collection tree and memberships with material IDs and reconstruct on import; validate ownership, paths, replay, cycles, conflicts, and evidence independence. Existing materials are initially uncategorized, not auto-classified.

## Starter templates and suggestions
Ship small versioned localized definitions as application data, not mandatory DB rows. Empty is first-class and can skip without loss. Templates: traditional chess topics (Openings, Middlegames, Endgames, Tactics, Strategy); learning levels; course scaffold. Example branches, not exhaustive curriculum. Before application show full structure, allow editing/excluding entries, name collision handling and explicit target root. Apply atomically; repeat request returns same receipt; independent new application must not silently duplicate or merge. Existing library unchanged unless explicit target and conflict choice. No automatic propagation of later template versions. Templates create no materials or skill observations.
For suggestions prefer existing teacher vocabulary and full paths, with bounded candidates and reason (material title/verified metadata/user context). Offer uncategorized as equally valid. Never treat AI suggestion as fact, or require classification to create or record a lesson. If teacher explicitly names a unique existing target, normal authorized operation can place it; no extra confirmation just because MCP is used. Clarify ambiguous names across parents; preview/confirm bulk restructuring, new template application, new inferred collections, archive subtree and consequential changes. No automatic organization on import or lesson capture. If coach says "save under Endgames > Rook endgames" and path missing, propose exact new path and get explicit approval before creation; direct clear request to create the specified path can authorize creation under usual safeguards. Do not block core lesson capture on optional categorization; offer follow-up separately. Never classify based on a student's name alone.

## Responsive UX
Library and Lichess are distinct views; All materials, derived Uncategorized, search by title/type/path, tree disclosure and breadcrumbs. Expand/collapse and select without navigating away on desktop; use existing three/two/one-column responsive shell, no compulsory fourth pane. Mobile drilldown preserves path, filters, scroll and back navigation. Category creation, rename, move, membership chooser, templates and archive preview accessible by keyboard and touch; no drag-only action. Details pane uses meaningful typography, chess board/PGN/FEN if verified, source links and actual learning evidence. Keep Lichess OAuth/credentials in trusted UI, existing study index, puzzle publication and explicit provider-write approval. Categorizing local material never modifies remote studies or creates teaching evidence. Support en/he/ru, RTL and arbitrary teacher-created multilingual names; don't translate user names silently.

## MCP/service surface (candidate naming)
Use task-oriented bounded read/search (tree/subtree, full paths, category filtered material catalog, memberships), preview and commit for tree operations, membership add/remove and bulk operations, template list/preview/apply, archive/restore and export. Exact ccp_* names and schemas reviewed against registry before implementation; reuse current material tools for actual material changes, no generic SQL executor. Stable IDs preferred for mutations, path resolution returns multiple candidates when ambiguous. Shared root-object schema, revisions, idempotency UUID, confirmations as warranted, explicit receipt counts and independent read-back. No new MCP secrets or permission bypass; scopes, teacher ownership and authenticated web/MCP parity required.

## Schema governance
Latest inspected main 35413fa: existing flat skill categories and typed materials have no hierarchical memberships. A dedicated model is a recommendation, not a settled physical schema. Review current baseline, ADR-0019 and successor lock (ADR-0037), decide schema amendment through separate reviewed ADR, update canonical baseline/types/manifest/lock only under that authority. No ad hoc feature migration; no live data or legacy adapters. Reconcile export/reimport of uncategorized existing materials; verify structural comparison, RLS, grants, isolation, concurrency, all required CI and restores before merge. Production migration/cutover requires separate operator authorization.
