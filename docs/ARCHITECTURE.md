# ChessCoachPal architecture and expansion roadmap

**Implemented today:** A self-hostable Next.js/TypeScript website; Supabase Auth + Postgres RLS; teacher-owned students, workplaces, classes, scheduled lessons, attendance, learning observations and selected chess study **URL references**; versioned OAuth/Streamable HTTP MCP gateway with **28 implemented tools**. The Vercel+Supabase demo was live-tested for endpoint discovery/auth/client registration, and real Codex created a synthetic student, workplace and enrollment. No production multi-teacher cloud service, Lichess Study API integration, online rating sync or official public ChatGPT plugin has been published.

**Source of truth:** The website and MCP adapters must invoke the same authenticated teacher-scoped domain service. Never expose a Supabase service-role key, Lichess token, guardian contacts or full student notes to a chat tool. Use scope-aware OAuth consent, RLS, stable IDs, optimistic revisions and idempotent receipts.

**Existing data-model discrepancy:** Inherited `lesson_slots` and `lessons` schedule one-to-one occurrences, while newer `teaching_sessions` + `session_participants` + `session_attendance` represent MCP coaching. Both exist in the current fresh schema. Their history and totals require reconciliation **before** adding arbitrary multi-student capture; 90 minutes concurrently teaching three people counts 90 minutes for the teacher, not 270.

**Planned (NOT implemented):** [Conversational lesson, Lichess materials and chess student profile OpenSpec](../openspec/changes/support-conversational-lesson-and-lichess-workflows/proposal.md) proposes English/Hebrew aliases while retaining canonical full Hebrew reporting name; 1–10 teacher strength, source-aware separate provider rating histories; recurring-time fallback; one transaction for shared lesson capture; selected studies/chapters by teacher/workplace/student; image-assisted FEN validation and approved Lichess chapter write/numbered rollover. Refer to [student model and phased architecture](MCP_WORKFLOW_ROADMAP.md) for exact scope and proposed MCP tools.

**Release and public distribution:** Current package is `0.0.0`; the v0.1.0 release-only change remains open. ADR-0001 deliberately offers no compatibility with CogNote or between pre-1.0 ChessCoachPal versions. **Public hosted SaaS and an official ChatGPT Plugin Directory listing are later product capabilities, default target at/after public v1.0.0 SaaS**, not automatic consequences of local deployment. The plugin can be submitted earlier as a hosted beta only after independent production/privacy/reviewer readiness. Self-hosting and Codex/Claude custom MCP use remain distinct; see [public plugin guide](PUBLIC_PLUGIN_SUBMISSION.md).


## Nonnegotiable MCP-first architecture rule (source audit 2026-11-08)

**The existing `/mcp` endpoint is the primary management interface for every ordinary teacher-owned business capability**, including generated reports; the website is only an optional visual presentation/editing/approval interface. All new website business features need same-PR typed MCP read/write (or documented narrow secure browser approval) and shared service-level validation. A site feature without an MCP equivalent is incomplete. See the [93-case parity checklist](MCP_WEBSITE_PARITY_CHECKLIST.md), [machine registry](../scripts/mcp-website-parity.json) and [OpenSpec delta](../openspec/changes/support-conversational-lesson-and-lichess-workflows/specs/teacher-workspace-mcp-parity/spec.md).

Static audit of current code: 61 API routes, 17 teacher pages, 49 teacher components and 28 existing tools; 43 teacher-business API route surfaces are **0 complete / 3 partial / 40 missing** when measured at whole-route parity. Do not conflate the 28 working tool names with full website support. Website reports currently call `lib/coaching-report.ts` but MCP has no report tool; proposed report actions MUST reuse that exact deterministic service. User account/password/MFA, payment provider credentials, guardian-originated flows and browser/device push require a separate secure authorization or authority; they cannot be exposed as raw chat CRUD. Normal CI checks inventory coverage, while GitHub Release runs a strict blocker. These safeguards do not replace actual authenticated website↔MCP behavioral tests.
