# Privacy, secrets and publication safety

## Private beta signup defense in depth (2026-11-16)

**Confirmed vulnerability before fix:** the live self-hosted GoTrue Auth server advertised `disable_signup=false` while the Next.js `/api/auth/signup` route required a `BETA_ACCESS_CODE`. A direct call to the public GoTrue `/auth/v1/signup` endpoint could therefore create an identity without passing the site's invite-code check. The teacher setup endpoint's existing guard limits some provisioning but does **not** secure Auth identity creation by itself.

**Fix in development:** keep the beta-code + waitlist UX; configure GoTrue `DISABLE_SIGNUP=true`, and only after verifying the server-only invite code create an Auth user via Supabase service-role `auth.admin.createUser`. Map `BETA_GOTRUE_SIGNUP_DISABLED` and `BETA_GOTRUE_EMAIL_AUTOCONFIRM` into the website from the same Compose environment values as Auth; the website refuses beta signup if either safety condition is not met. Admin user creation uses `email_confirm=true` only while the operator intentionally enables auto-confirm; it does not email confirmation links, and does **not** constitute verified email ownership. Secure email confirmation/invitation requires a separate tested mail-delivery flow (SendPulse is owner-configured later).

**Acceptance:** isolated Compose must reject direct unauthenticated GoTrue signup without inserting an identity; reject absent/incorrect invite code; accept valid code and provision teacher exactly once; persist a public waitlist email through its rate-limited server route; preserve existing login and public self-hosted signup where beta mode is disabled. The live endpoint `/auth/v1/settings` must say `disable_signup=true` after the fix is deployed. No database reset or new broad RLS grant is permitted. The source-code change alone is **not** evidence that the live GoTrue setting was changed.


## 2026-11-15 live Supabase advisor and canonical schema audit

[PR #81](https://github.com/itshak/ChessCoachPal/pull/81) carries a **single canonical baseline** update with a corresponding transactional hardening change applied to the test Supabase project. No test-teacher/student/material rows were deleted by this hardening; the current pre-v1 snapshot remains `supabase/migrations/20261107000000_chesscoachpal_baseline.sql`.

**Verified improvements:** fixed search paths on 8 inherited functions, revoked `anon`/`authenticated` direct EXECUTE on 11 **trigger-only** `SECURITY DEFINER` functions, optimized 63 live ownership policies including session-setting initialization plans (66 CREATE POLICY definitions in the baseline), and added 59 indexed FK constraints flagged by Supabase. The follow-up Security Advisor showed **zero anonymous security-definer RPC warnings and zero mutable search-path warnings**; Performance Advisor showed **zero unindexed-FK and zero auth RLS initplan warnings**. An authenticated student-update SQL transaction was run and rolled back successfully after hardening; the test material's two independent links were queried separately.

**Intentional/unresolved advisor findings (do not conceal):** 13 RLS-enabled server-only tables have **no client policies**, an intentional deny boundary, not an invitation to add permissive `SELECT` policies; the rate-limited public waitlist uses a service-role route and its unnecessary `authenticated` table grants were additionally revoked in the canonical baseline and hosted test DB; the advisor still reports 40 authenticated-executable SECURITY DEFINER functions (the observed advisory count after revoking internal trigger-only routines) because authorized teacher-owned RPCs are intentionally part of the REST business API—each must preserve strong `auth.uid()`/tenant authorization and denial tests. `unused_index` is informational for a tiny new dataset; benchmark before dropping defensive FK indexes. Supabase leaked-password protection remains a hosted **Auth configuration** warning, documented by Supabase as available on **Pro and above**; it cannot be enabled via the canonical SQL and requires the eligible operator's dashboard action. Do not claim that all advisor warnings are zero or that every privileged RPC has been manually threat-modeled.

**Operational hazards:** direct SQL deletion of Supabase Storage objects/buckets hits protected internal triggers; surviving `storage.objects` avatar policies must be handled on an expressly approved disposable reset. App-schema DDL and `supabase_migrations.schema_migrations` history are distinct. Never reset a real-student database implicitly. See [ADR-0007](adr/0007-mcp-supabase-contract-and-release-evidence.md), [operator/portable runbook](MCP_SUPABASE_RELIABILITY_PLAYBOOK.md), [applied spec](../openspec/specs/chess-only-security/spec.md) and [Supabase password security docs](https://supabase.com/docs/guides/auth/password-security).
