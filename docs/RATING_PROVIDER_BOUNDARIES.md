# Rating-provider boundaries for ChessCoachPal

**Proposal for review; no implementation or schema change.** This is the shared architecture for the existing [FIDE and national ratings OpenSpec](../openspec/changes/2026-11-18-introduce-fide-national-ratings/proposal.md) and [online rating sync OpenSpec](../openspec/changes/2026-11-18-automate-online-rating-sync/proposal.md). It adds no third feature change. The [consolidated P0](../openspec/changes/archive/2026-11-21-consolidate-final-preproduction-saas-schema/proposal.md) remains the sole DDL owner. Downstream implementation starts only after the freeze. If the transactional checks below genuinely require a new database contract, raise that as an explicit freeze decision rather than adding feature-owned DDL.

## Decision: separate provider code, keep one application service

Start with server-only adapters and a bounded worker in the existing repository, not independent HTTP microservices. Provider differences are real; ownership, approval, data writing, and API/MCP contracts should not drift across them.

| Boundary | Owns | Does not own |
| --- | --- | --- |
| Rating domain/application | Tenant and active-student checks, confirmed player-ID/handle linking, consent and revision policy, review/digest and idempotency, immutable snapshot writes, read-back and history | Remote protocol, source-specific parsing or backoff details |
| Online account adapters | One adapter each for Lichess and Chess.com. Public account lookup, provider category mapping, provider rate limits and typed remote outcomes | Tenant IDs, student profile writes, private games, credentials or consent decisions |
| Official-list adapters | FIDE publication download and parsing by edition; an adapter per national federation only once its source and access are approved. Lookup by exact provider player ID | Guessing identity by name, editing a linked student, writing shared ratings independently |
| Scheduling and transport | One operator-controlled execution boundary. Bounded per-provider queues/budgets, timeouts, fixed allowlisted hosts, retry/backoff, status and observability | Reusing the online identity queue for federations or inventing a second store of student ratings |

FIDE needs a different retrieval method, not a different application. Prefer a single fetch per official edition, verify and record its source/digest, and use an indexed or cached exact-ID lookup. Check the [official FIDE list downloads](https://ratings.fide.com/download_lists.phtml) and confirm allowed use, caching/retention and redistribution before enabling automation. Do not poll profile pages for every student. For the Israeli federation, keep attributed manual evidence and source links until an approved feed and terms are verified; other national federations follow the same rule. Online adapters use the [Lichess API](https://lichess-org.github.io/api/) and [Chess.com Published Data API](https://support.chess.com/en/articles/9650547-what-is-the-pubapi-and-how-do-i-use-it) under their own request limits and access rules. Fixed provider URLs and public IDs only; never send a student's name, contact details, tenant ID, or internal identifiers to resolve a rating. Avoid storing full upstream payloads by default; any reusable federation edition cache contains no tenant-to-student associations.

### Contract and storage

- Each adapter accepts a validated provider ID or handle, plus a known list edition where applicable. It returns normalized observations or an explicit outcome: missing account, category not published/unrated, malformed data, rate-limited with a retry hint when available, or temporarily unavailable. Return category, value, provenance and applicable dates; a missing value is not a zero or a reason to erase a previous valid observation. Keep provider category keys distinct, e.g. FIDE Standard and Lichess Classical.
- Both website and MCP call the same application operations. An external lookup supplies evidence for the **linked** identity; it does not verify that the account belongs to the student. Shared policy rechecks ownership, consent/confirmation, active-student eligibility and identity revision before fetching and before persistence. Automatic work must also recheck its lease and current authorization at commit, so revocation or a changed identity cannot append stale observations. Never infer consent from a saved handle or FIDE ID. No rating alters teacher-assessed strength, mastery, or other educational evidence.
- Keep `rating_providers`, `rating_categories` and `student_rating_snapshots` as the authoritative registry and immutable student evidence. Official federation records use existing external ID, edition/list version, effective/observed/fetched timestamps and source digest fields. Manual evidence remains distinguishable. Online `student_rating_sync_consents`, `student_rating_refresh_jobs` and receipts currently constrain provider to Lichess/Chess.com and require username plus consent fields. **Do not insert federation records into that queue**, fabricate a username, or widen its constraints from a downstream feature. Use an operator-controlled edition refresh, with reviewed tenant matching/recording using the existing federation and snapshot model. Any future automatic per-learner federation workflow requires a specific authorization and atomicity review first.
- **P0 provenance candidate:** the canonical baseline candidate distinguishes manual, online and official-list evidence and enforces the registered provider kind at the database boundary. An official federation record uses its external player ID and list evidence, not the online username or preview digest. This source proof is not a freeze or authorization to fetch a live edition.
- **Source revision is not identity correction.** FIDE’s [2 March 2026 notice](https://www.fide.com/fide-march-2026-rating-list-correction/) corrected the March list and changed a player's active status; it does not establish that a revised ZIP is available. If an authorized source provides evidence of an actual revised release, retain both verified edition tokens and digests under the same player ID and effective period. Exact replay stays idempotent; do not promote an unverified changed digest, sort revision tokens lexically, or use fetch time as proof of precedence. Only promote the verified latest edition after a complete valid parse; failed or partial input leaves the last successful projection intact. Project one chart point per period and category, with no extra point for unchanged values. Activity and rating availability are separate. A published numeric rating stays visible even when explicitly inactive; only source-documented category activity may be presented. Missing and unrated are nonnumeric, never zero. Incomplete source coverage or zero games in one edition proves neither unrating nor inactivity. A teacher correcting the linked player ID must not fabricate a new release token to bypass the same-edition key.
- **Teacher ID correction in the same list.** The candidate deduplicates by teacher, student, provider, category, and list version, not external player ID. Preserve the old row as history, exclude it from the current summary after the linked ID changes, and flag a same-edition replacement as unavailable until a verified newer edition. Do not spoof a release token. If same-edition replacement is required at launch, review the key and explicit audit semantics under P0 before freeze.
- **Online worker boundary in the P0 candidate.** The service-only `ccp_rating_refresh_claim` and `ccp_rating_refresh_finalize` functions lock/revalidate the current student, handle binding, consent and lease, then commit normalized snapshots, one attempt receipt and job state in one transaction. Identity changes and consent revocation advance the binding epoch, so regrant or changing away and back cannot resurrect an earlier job. Provider HTTP stays outside SQL and the service must recheck eligibility immediately before fetching. No cron, provider call or consent is enabled by these primitives. The downstream enqueue must be durable or safely reconciled, and its recorded creation time cannot precede the consent granting that handle.
- Keep current website/MCP shapes stable when extracting adapter code. Preserve replay before network calls and the current fail-closed behaviors. Reuse the existing parsers in `lib/chess-public-ratings.ts`, the owner-scoped operations in `lib/server/student-rating-snapshots.ts`, and the federation identity/manual service in `lib/server/student-federations-service.ts`. New provider formats should not require editing core lookup logic, changing the SQL baseline, or adding client-side outbound requests.

## Order and acceptance

Follow the [reconciled roadmap](OPENSPEC_RECONCILED_EXECUTION_SEQUENCE_2026-11-19.md#critical-path): freeze the shared schema first and complete the earlier foundation stages before starting rating work.

1. **Federation identity and official evidence first.** Complete exact FIDE/national ID linking and manual/verified evidence. Use synthetic edition fixtures for indexed lookup, replay, verified same-period corrections, and nonnumeric outcomes. Enable live parsing only after source and usage approval. Prove the same website/MCP operations and audit read-back.
2. **Online adapters and refresh second.** Extract existing Lichess and Chess.com transports behind their unchanged preview/commit operations, then complete consent, scheduling and worker behavior on the online queue only. Test provider limits, stale/missing data, duplicate deliveries, lease and identity changes, revoked consent, tenant boundaries and independent read-back. Use recorded/synthetic fixtures; CI does not need live providers.

Revisit a separately deployed worker, still from this repository, only when measured edition processing exceeds request time/memory budgets, provider traffic affects the app, or a separate outbound permission boundary is required. Do not create a separate data plane or remote service per provider without that evidence.

### Offline edition acceptance fixture

The unwired synthetic adapter in `lib/server/federation-ratings/synthetic-fide-editions.mjs` is an executable acceptance contract, not an implementation of a FIDE file format. It accepts only its marked synthetic envelope, bounded bytes/records/editions, and separate caller-supplied test metadata for the SHA-256, date, category coverage and activity capability. Lookup requires an exact linked numeric ID and category. Explicitly inactive observations retain their numeric ratings; a generic flag cannot imply category activity. Partial or absent category coverage cannot replace current evidence, and missing, explicit unrated and unknown coverage remain distinct. A valid same-period correction must reference its accepted predecessor; same-token replay is stable, changed evidence conflicts, and incomparable revisions leave no current winner. The latest expected period is an explicit input, so a prior period can remain last-known and stale rather than posing as current.

Run `node --test lib/server/federation-ratings/synthetic-fide-editions.test.mjs`. The contract makes no requests, accepts no provider files, writes no snapshots, and does not change the website/MCP read path, schema, or authorization. Before any provider adapter or durable storage, verify exact approved format, availability/completeness and revision evidence, allowed use/caching/redistribution, consent and tenant commit checks, and separately approved operator rollout. The synthetic descriptor is not proof of provider authority.
